The entity API has two layers:

| Layer | Use it when |
| --- | --- |
| `Entity<T>` | You have a Java record type and want typed reads and writes |
| `Records` | You need dynamic fields, transfers, migrations, or runtime schemas |

Both layers use the same query, predicate, mutation, and paging types.

## Typed Entities

```java title="TypedEntity.java"
var accounts = tava.entity(Account.class);

Account saved = accounts.insert(new Account(
        UUID.randomUUID(),
        "ada@example.com",
        7,
        null
));

Optional<Account> found = accounts.findOne(Predicate.eq("email", saved.email()));

var page = accounts.find(Query.builder()
        .where(Predicate.eq("email", saved.email()))
        .limit(1)
        .build());
```

`Entity<T>` maps between the record type and `EntityRecord` internally. Insert calls
return the stored record, which is useful when the backend generates fields.

Pass a name separately when the same record schema is used for tenant, shard, archive,
or version-specific storage:

```java
Entity<Account> archived = tava.entity("accounts_2025", Account.class);
```

The record annotations still define fields and mapping; only the target entity name is
overridden.

## Dynamic Records

```java title="DynamicRecords.java"
import eu.mikart.tava.data.EntityRecord;

var records = tava.records("accounts");

records.insert(EntityRecord.builder()
        .set("id", UUID.randomUUID())
        .set("email", "grace@example.com")
        .set("score", 11)
        .build());
```

Use `Records` for migration code, data transfer transforms, admin tools, or schemas
that are not represented by Java record classes.

## Predicates

Predicates are composable and backend-neutral.

```java title="Predicates.java"
Predicate activeHighValue = Predicate.and(
        Predicate.eq("status", "active"),
        Predicate.gte("score", 100)
);

Predicate named = Predicate.or(
        Predicate.startsWith("email", "ops@"),
        Predicate.contains("tags", "internal")
);
```

| Predicate | Purpose |
| --- | --- |
| `all()` | Match every record |
| `eq(field, value)` | Equality |
| `ne(field, value)` | Inequality |
| `lt`, `lte`, `gt`, `gte` | Ordered comparisons |
| `in(field, values)` | Field is one of several values |
| `contains(field, value)` | Backend-supported containment |
| `startsWith(field, value)` | Prefix matching |
| `isNull(field)` | Field is null or absent |
| `isNotNull(field)` | Field is present and non-null |
| `and(...)`, `or(...)` | Junctions |

`in(...)`, `and(...)`, and `or(...)` require at least one value or predicate. This
keeps their meaning portable and prevents adapters from producing invalid native
queries. `contains(...)` follows the backend's value semantics: it can mean a
substring or a collection member, depending on the field and adapter.

## Sorting, Projection, And Limits

```java title="QueryBuilder.java"
var query = Query.builder()
        .where(Predicate.eq("status", "active"))
        .project("id", "email", "createdAt")
        .sort(Sort.desc("createdAt"))
        .limit(50)
        .build();
```

`project(...)` narrows the returned fields. `sort(...)` accepts one or more
`Sort.asc(...)` or `Sort.desc(...)` values. `limit(0)` means the adapter default is
used.

## Cursor Paging

Find calls return a `Page<T>` with the current items and an optional cursor for the
next page.

```java title="Paging.java"
String cursor = null;

do {
    var page = accounts.find(Query.builder()
            .where(Predicate.eq("status", "active"))
            .sort(Sort.asc("email"))
            .limit(500)
            .cursor(cursor)
            .build());

    for (Account account : page.items()) {
        export(account);
    }

    cursor = page.nextCursor();
} while (cursor != null);
```

Treat cursors as opaque values and pass them back with the same filter, sort, projection,
and page size on the same adapter and entity. Changing any of these invalidates the cursor. Cursors
continue the result ordering; they are not a database snapshot. Inserts, deletes, or
changes to sort values while paging may affect later pages. When sorting, include a
stable unique field if your application needs repeatable ordering across runs.

## Updates And Deletes

Updates use `Mutation`. Deletes use a predicate directly.

```java title="Mutate.java"
long updated = accounts.update(
        Predicate.eq("email", "ada@example.com"),
        Mutation.builder()
                .set("score", 8)
                .build()
);

long deleted = accounts.delete(Predicate.eq("status", "disabled"));
```

<Callout type="warn" title="Predicate scope matters">
`update` and `delete` operate on every record matched by the predicate. Build admin
workflows so broad predicates are deliberate and visible.
</Callout>

## Identities and upserts

`@Identity` drives typed ID operations. A record may have one identity field or a
composite identity made from several fields.

```java
var account = accounts.findById(accountId);       // Optional<Account>
boolean present = accounts.existsById(accountId);
MutationResult result = accounts.updateById(accountId, mutation);
accounts.deleteById(accountId);

// Named values make composite keys unambiguous.
var key = Identity.of(Map.of("userId", userId, "emblemId", emblemId));
tava.records("unlocked_emblems").findById(key);
```

`upsert(record)` is one logical atomic operation. MongoDB uses a native upsert;
JDBC adapters execute it within one transaction and retry the update if a concurrent
insert wins. For an explicit outcome, use `insertResult`, `updateResult`, or
`deleteById`; `MutationResult` reports matched rows, changed rows, conflicts, and an
`INSERTED`, `UPDATED`, `DELETED`, `UNCHANGED`, or `CONFLICT` outcome. A count of `-1`
means the adapter cannot report that count. Conflict details are portable when the
adapter can identify them.

Use `insertIfAbsent(record)` when an existing unique key is expected rather than
exceptional. A conflict result contains portable `ConflictDetail` entries (kind,
constraint when known, backend code, and message), so callers do not need to inspect a
driver exception.

## Typed Fields and Atomic Mutations

Add the core artifact to the annotation processor path to generate field companions
for top-level, non-generic records annotated with `@Entity`:

```kotlin
dependencies {
    annotationProcessor("eu.mikart.tava:tava-core:1.3.0")
}
```

For `Account`, the processor generates `AccountFields`. Fields retain their Java types
(including collection element types), and `@Field` storage names are resolved once:

```java
var query = Query.builder()
        .where(AccountFields.score.gte(100))
        .sort(AccountFields.createdAt.desc())
        .limit(50)
        .build();

Mutation mutation = Mutation.builder()
        .increment(AccountFields.score, 1)
        .build();

for (var page : accounts.pages(query)) {
    page.items().forEach(this::export);
}
```

Page traversal binds the original query and entity to its continuation tokens. It is
lazy, single-use, and preserves filtering, sorting, projection and page size. Streams
use the same traversal. For explicit token handling, `query.withCursor(token)` copies
the original request with a new token.

Fields may also be declared without code generation:

```java
var score = FieldRef.of(Account.class, "score", Integer.class);
FieldRef<Collection<UUID>> emblems = FieldRef.collection("emblems", UUID.class);
var mutation = Mutation.builder()
        .increment(score, 1)
        .appendIfAbsent(emblems, emblemId)
        .remove(emblems, retiredEmblemId)
        .build();
```

Record-aware references validate the declared component type and resolve `@Field` names.
String references remain available for dynamic schemas. Typed references support
comparisons, membership, null checks, sorting and projections; collection element types
help compilation but do not validate values already stored in a database.

`increment`, `appendIfAbsent`, and `remove` are database operations. Unsupported operators
throw `TavaException.Capability`; typed expressions do not imply backend support.
`contains` retains the adapter's string or collection semantics. The deprecated
`append(...)` alias retains its existing conditional behavior.

## Transactions and asynchronous calls

Callback transactions commit when the callback returns and roll back when it throws.
They are implemented by JDBC and MongoDB adapters. The transaction-scoped `Tava`
handle is valid only on the callback thread, only until the callback returns; nested
transactions, schema changes, native access, and async calls are unavailable inside
the callback:

```java
tava.transaction(tx -> {
    tx.entity(Account.class).updateById(id, mutation);
    tx.entity(AuditEvent.class).insert(event);
    return null;
});
```

Synchronous I/O entry points carry `@Blocking`. Async methods such as
`findByIdAsync`, `insertAsync`, and `upsertAsync` use the executor supplied to
`Tava.open(adapter, executor)`; `Tava.open(adapter)` uses virtual threads for blocking database I/O.
Server and game applications should provide a dedicated database executor rather
than use their main/event-loop thread. Closing `Tava` waits for active operations to
finish and closes its adapter. `tava.close(Duration.ofSeconds(10))` bounds the wait
for active operations and returns `false` on timeout, leaving the instance open. Driver
cleanup itself still uses the driver's timeout policy. Do not close it from inside an active operation.

## Value mapping and errors

UUID, enum, `Instant`, `OffsetDateTime`, `LocalDate`, and `LocalDateTime` values map
natively. Typed enum collections are recursively converted as well; JDBC stores
collections and maps as JSON while document adapters retain native collection values.
`ValueCodecs.enumName(...)`, `list(...)`, and `set(...)` are available for reusable
custom mappings. Nested records map as embedded documents. Add
`@MappedWith(MyCodec.class)` to a component for custom encoding. All public failures
derive from `TavaException`; its `Capability`, `Schema`, `Mapping`, `Data`, `Conflict`,
`Connection`, and `Transaction` subtypes let applications handle failures consistently
without depending on `SQLException`.

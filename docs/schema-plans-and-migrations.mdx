description: Define previous and next schemas, author both migration directions, and move between versions.

`SchemaHistory` owns schema evolution. Define versions once in application order, with
an `up` path and a `down` path for each reversible transition. Each action receives the
same chronological `previous()` and `next()` snapshots in either direction.

```java
SchemaHistory history = SchemaHistory.builder()
        .version("001-accounts", accountsV1, change -> change
                .up(context -> context.apply(context.next()))
                .down(context -> dropAccounts(context)))
        .version("002-display-name", accountsV2, change -> change
                .up(context -> context.apply(context.next(), SchemaRenames.builder()
                        .field("accounts", "name", "display_name")
                        .build()))
                .down(context -> context.apply(context.previous(), SchemaRenames.builder()
                        .field("accounts", "display_name", "name")
                        .build())))
        .build();

history.up(database);                         // run all pending versions, one by one
history.down(database);                       // undo the latest version
history.to(database, "001-accounts");          // move forward or backward to this version
Optional<String> current = history.current(database);
```

`dropAccounts` in this example is a developer-defined operation using the chosen
adapter's native client. Schema snapshots do not infer a drop, a conversion or a
rollback. For JDBC, that helper could execute `DROP TABLE IF EXISTS "accounts"`
through `context.nativeAccess().withNative(Connection.class, ...)`. Explicit rename
mappings are supported by JDBC adapters.

The old migration manager, migration status, result and lock-info types have been
removed. The history is the execution interface; `current(...)` returns only the
version identifier and never creates storage.

## Schema and Data Actions

Declare separate actions in the order they should run. Down actions execute in their
own declaration order; versions are undone in reverse order.

```java
.version("003-normalize-status", accountsV3, change -> change
        .up("Add status", context -> context.apply(context.next()))
        .up("Backfill status", context -> context.records("accounts").update(
                Predicate.isNull("status"),
                Mutation.builder().set("status", "active").build()))
        .down("Remove status", context -> removeStatusField(context)))
```

Use `context.records(...)`, `context.entity(...)`, `context.nativeAccess()` and
`context.database()` for database work. `context.apply(...)` supports safe additive
changes, explicit rename mappings, or named risk allowances with `ApplyOptions`.
The developer authors conversions, backfills, removals and data validation. Removing a
field, changing its type or strengthening nullability may need native operations when
the adapter's schema planner cannot provide that operation.

At least one up action is required. A version without down actions is explicitly
forward-only. Before moving backward, the entire requested route is checked for
missing down paths, so an irreversible version cannot leave a partially undone route.
Rolling back the first version returns to the empty schema. Calling `down(...)` when
no version is applied is a no-op.

After each transition, Tava checks the target using the adapter's planner and inspects
removals observable through its schema metadata. Simply applying an older additive
schema does not complete a rollback if the newer entities or fields remain. These
checks cannot prove data invariants or document shapes that the adapter cannot inspect.

## History and Retries

Bundle fixed historical schemas with the application. Use separate historical record
classes or schema builders; do not rebuild an older snapshot from today's evolving
record class. Tava freezes nested settings and rejects unsupported mutable values.
Identifiers must be unique, and declaration order determines execution order.

Schema checksums, ordering, locks and step checkpoints are managed internally. Calling
`up(...)` twice skips versions already applied. Calling the same operation again after
an action fails resumes at the interrupted action, without rerunning completed actions.
An incomplete transition must finish before changing direction. Target verification
also retries automatically and cannot be skipped.

An interrupted action may have changed data before its checkpoint was saved. **Author
actions so that retrying them is safe**, using idempotent assignments, upserts, or native
operations with equivalent behavior. Automatic resumption does not imply exactly-once
side effects or one transaction across all versions.

Tava automatically fingerprints schemas, predecessor versions and action declarations.
To detect changes to callback implementation code as well, optionally set
`change.checksum(MigrationChecksums.sha256(source))` using immutable source content.
Changing a recorded schema or supplied digest rejects execution before another action
runs. Java lambda implementations cannot be hashed reliably by the library.

Initial application refuses existing managed storage with no recorded history;
unrelated storage is preserved. Use `SchemaHistory.builder().journal("other_history")`
for an independently managed history. The default journal is `_tava_migrations`.
A process crash can leave its durable lock behind. An operator must verify the runner
has stopped before removing that journal's `__tava_migration_lock__` record through
native administrative access. Locks are never stolen based on a timeout.

## Simple Setup and Inspection

For safe additive setup in disposable databases, use:

```java
database.schema().ensure(Schema.of(Account.class));
```

Low-level `database.plan(schema)` and `planExact(schema)` remain available for schema
inspection. `SchemaPlan.apply()` rejects lossy, destructive and unsupported changes.
`ApplyOptions.allowing(ChangeRisk.LOSSY)` or `ChangeRisk.DESTRUCTIVE` names the risks
explicitly; unsupported changes cannot be allowed. Exact planning reports omitted
storage but adapters currently mark automatic removals unsupported. History down
actions perform their explicitly authored removals instead.

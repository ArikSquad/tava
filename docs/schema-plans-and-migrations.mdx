Tava separates planning from application. Adapters produce a `SchemaPlan`, the plan
reports its changes, and `apply(...)` enforces risk rules before touching storage.

## Plan First

```java title="PlanSchema.java"
SchemaPlan plan = tava.plan(schema);

for (SchemaChange change : plan.changes()) {
    System.out.printf("%s %s%n", change.risk(), change.description());
}

plan.apply();
```

Planning is read-only: inspect the changes before calling `apply()`. `tava.plan(schema)`
plans changes needed to reach the desired schema while leaving unrelated storage alone.
Use `tava.planExact(schema)` when the desired schema is the complete inventory for the
namespace. Exact planning also reports entities, fields, and indexes missing from the
desired schema. Current adapters mark those removals `UNSUPPORTED`, so they are visible
in the plan but are not applied. Exact planning is available only on adapters that
implement it: JDBC, MongoDB, and DynamoDB in 1.3.0.

## Risk Levels

| Risk | Default behavior |
| --- | --- |
| `SAFE` | Applies with `plan.apply()` |
| `LOSSY` | Requires `new ApplyOptions(true, false)` |
| `DESTRUCTIVE` | Requires `new ApplyOptions(false, true)` or both flags |
| `UNSUPPORTED` | Never applies |

```java title="ApplyOptions.java"
import eu.mikart.tava.schema.plan.ApplyOptions;

plan.apply(ApplyOptions.safe());
plan.apply(new ApplyOptions(true, false));  // allow lossy changes
plan.apply(new ApplyOptions(false, true));  // allow destructive changes
plan.apply(new ApplyOptions(true, true));   // allow both
```

## Adopt Renamed JDBC Schemas

When an existing table or column already represents the desired model under an older
name, supply explicit old-to-new mappings. This prevents the planner from creating a
second table or column:

```java
SchemaRenames renames = SchemaRenames.builder()
        .entity("player", "players")
        .field("players", "emblems_csv", "emblems")
        .build();

SchemaPlan plan = tava.plan(desiredSchema, renames);
plan.apply();
```

Field mappings use the final entity name. Rename mappings are currently implemented by
JDBC adapters; unsupported adapters reject non-empty mappings explicitly.

<Callout type="warn" title="Loss is explicit">
The default path is safe. If a change can discard data or remove storage, the caller
has to say so in code.
</Callout>

## One-Off Migrations

For small applications, a migration can simply be a schema.

```java title="SchemaMigration.java"
import eu.mikart.tava.migration.Migration;

var migration = Migration.up("2026-01-15-create-accounts", schema);

tava.migrations().apply(migration);
```

Tava records applied migrations in `_tava_migrations` unless you construct
`Migrations` with a custom metadata entity.

## Multi-Step Migrations

Use the builder when schema changes and data changes need to run together.

```java title="DataMigration.java"
import eu.mikart.tava.migration.Migration;
import eu.mikart.tava.query.Mutation;
import eu.mikart.tava.query.Predicate;
import eu.mikart.tava.query.Query;

Migration migration = Migration.builder("2026-02-02-normalize-accounts")
        .upSchema(nextSchema)
        .up("Backfill missing scores", context -> context.update(
                "accounts",
                Predicate.eq("score", null),
                Mutation.builder().set("score", 0).build()))
        .up("Visit active accounts", context -> context.forEach(
                "accounts",
                Query.builder().where(Predicate.eq("status", "active")).build(),
                record -> audit(record.get("id"))))
        .build();

var results = tava.migrations().apply(migration);
```

Migration steps run in order. Each step records an operation result, and schema steps
include the `SchemaChange` values produced by the adapter.

## Rollbacks

Rollbacks require a down path.

```java title="Rollback.java"
Migration migration = Migration.reversible(
        "2026-03-04-add-account-status",
        schemaWithStatus,
        schemaWithoutStatus
);

tava.migrations().apply(migration);
tava.migrations().rollback(migration);
```

If a migration has no down schema or down action, `rollback(...)` rejects it.

## Inspect and Recover Migration State

```java title="MigrationState.java"
List<String> applied = tava.migrations().applied();
List<Migration> pending = tava.migrations().pending(allMigrations);
```

In 1.3.0 the journal records each migration's direction, state, checksum, and completed
step count. Inspect an interrupted migration before resuming it:

```java title="RecoverMigration.java"
var migrations = tava.migrations();
MigrationStatus status = migrations.status(migration.id()).orElseThrow();

if (status.state() == MigrationStatus.State.FAILED
        || status.state() == MigrationStatus.State.RUNNING) {
    migrations.resume(migration, Migrations.Recovery.RETRY_INCOMPLETE_STEP);
}
```

`RETRY_INCOMPLETE_STEP` reruns the step that was active when the process stopped;
`SKIP_INCOMPLETE_STEP` treats that step as complete and continues. Choose based on the
step's side effects: a step may have changed data before the process failed. Make
retriable actions idempotent where possible. Keep migration IDs stable and do not edit
an applied migration. An optional checksum lets Tava reject a changed definition:

```java
Migration migration = Migration.builder("2026-03-04-add-account-status")
        .checksum(generatedMigrationDigest)
        .upSchema(schemaWithStatus)
        .build();
```

Only set a checksum that stays identical for the same migration content.

Migrations are protected by a durable lock. If a process dies and leaves a lock behind,
`migrations.lock()` shows its owner token. Verify that the original migration process
has stopped before releasing that exact lock with `migrations.releaseLock(lockInfo)`;
locks do not expire automatically. This is an operator recovery action, not a routine
cleanup step.
